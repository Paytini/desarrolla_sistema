# UUID Primary Keys — Plan 1: Schema, Migration & Prisma Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convert all 16 Prisma models' primary keys (and every column referencing them) from `Int @default(autoincrement())` to `String @db.Uuid` backed by Postgres's native `gen_random_uuid()`, and land the new `Certificate.folio_sequence` column — with the live database migrated and a working, freshly-regenerated Prisma Client to prove it.

**Architecture:** One hand-verified SQL migration, applied via the repo's established `migrate diff` + manual `migrate deploy` workaround (this repo's `migrate dev` is permanently broken by unrelated shadow-DB drift). The migration is destructive by design — it truncates all 16 affected tables before changing column types, because the user confirmed the database holds only disposable test data (see spec §6). This plan does **not** touch application code (routes, server actions, libs) — that is Plan 2+. Expect `npx tsc --noEmit` to fail extensively across the app the moment the new Prisma Client is generated; that failure list is the direct input Plan 2 will consume. This plan's own pass/fail bar is: the DB reflects the new schema exactly, and a direct Prisma Client smoke script can create and read back a row with a real UUID primary key.

**Tech Stack:** Prisma 7 (`@prisma/adapter-pg`), PostgreSQL (Supabase), Node/TypeScript.

**Spec:** `docs/superpowers/specs/2026-08-18-random-uuid-ids-design.md`

## Global Constraints

- All 16 models get UUID primary keys, no exceptions (spec §2): `User`, `Notification`, `Company`, `Package`, `PackageCourse`, `CourseDc3Metadata`, `CompanyPackage`, `ConsultingRequest`, `Employee`, `EmployeeCourse`, `Certificate`, `IntegrationState`, `PortalSession`, `AuditEvent`, `SeatHistory`, `Job`.
- Every `wp_*` column stays `Int` — these are WordPress/Tutor LMS's own IDs, never migrated (spec §3): `User.wp_user_id`, `Employee.wp_user_id`, `Package.wp_bundle_id`, `PackageCourse.wp_course_id`, `CourseDc3Metadata.wp_course_id`, `EmployeeCourse.wp_course_id`, `Certificate.wp_course_id`.
- UUID format is v4, native Postgres `uuid` column type, default generated by Postgres itself via `@default(dbgenerated("gen_random_uuid()"))` — not `@default(uuid())`, which is Prisma-Client-side only and would not cover raw-SQL insert paths like `load-testing/seeders/*.js` (spec §4).
- Migration strategy is truncate-and-rebuild, not value-preserving — confirmed acceptable by the user because there is no production data yet (spec §6).
- `Certificate` gets a new `folio_sequence Int @default(autoincrement())` column, decoupled from `id`, for the official DC-3 folio format (spec §5). This plan only adds the column; updating `buildCertificateFolio()` to use it is Plan 2's job.
- Never use `prisma migrate dev` in this repo (broken shadow-DB replay, unrelated pre-existing drift). Use `prisma migrate diff --from-config-datasource --to-schema=prisma/schema.prisma --script`, hand-verify the output, apply via `prisma migrate deploy`. Note the `--from-config-datasource` flag is Prisma 7 syntax (replaces the older `--from-url "$DIRECT_URL"` — the old flag no longer exists in the installed `prisma@^7.7.0`).
- No test suite exists in this repo. Verification is: SQL introspection queries against the live DB, `npx prisma validate`, and a throwaway Node smoke script exercising the regenerated Prisma Client — all specified verbatim below, nothing to invent.

import { PrismaClient } from "@prisma/client"

const prisma = new PrismaClient()
const UUID_RE = /^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i

async function main() {

    data: {
      name: "Smoke Test Co",
      slug: `smoke-test-${Date.now()}`,
      hr_email: `smoke-${Date.now()}@example.com`,
      contracted_seats: 10,

  if (!UUID_RE.test(company.id)) throw new Error("company.id is not a valid UUID v4")

  const employee = await prisma.employee.create({
    data: {
      company_id: company.id,
      first_name: "Smoke",
      last_name: "Test",
      email: `smoke-employee-${Date.now()}@example.com`,
    },
  })
  console.log("employee.id:", employee.id, "employee.company_id:", employee.company_id)
  if (employee.company_id !== company.id) throw new Error("FK round-trip mismatch")

  const cert = await prisma.certificate.create({
    data: {
      employee_id: employee.id,
      wp_course_id: 999,
      course_name: "Smoke Test Course",
      reference_number: `SMOKE-${Date.now()}`,
    },

  console.log("certificate.id:", cert.id, "certificate.folio_sequence:", cert.folio_sequence, "typeof folio_sequence:", typeof cert.folio_sequence)
  if (typeof cert.folio_sequence !== "number") throw new Error("folio_sequence did not auto-increment as a number")

  await prisma.certificate.delete({ where: { id: cert.id } })
  await prisma.employee.delete({ where: { id: employee.id } })
  await prisma.company.delete({ where: { id: company.id } })
  console.log("PASS: cleaned up smoke-test rows")
}

main()
