# Random (UUID) Primary Keys — Design

**Date:** 2026-08-18
**Status:** Approved by user, ready for implementation planning.

## 1. Problem

Every primary key in the database is `Int @id @default(autoincrement())` — sequential, starting at 1. Four routes expose an entity's ID (or a name-derived slug) in the URL: `/superadmin/companies/[id]`, `/superadmin/packages/[id]`, `/api/certificates/[id]`, `/company/[slug]`. An attacker (or a curious/malicious authenticated user) can enumerate these — try `/api/certificates/1`, `/api/certificates/2`, ... — to probe for the existence and approximate volume of records, even where authorization checks correctly block access to the *content*.

**Audit finding, not assumed:** all four exposed routes were checked before this design was written.
- `/superadmin/companies/[id]`, `/superadmin/packages/[id]` — gated by `rol === "SUPERADMIN"`; low risk (internal staff only).
- `/api/certificates/[id]` — has an ownership check (`isOwner`/`isCompanyHr`/`isSuperAdmin`); a guessed ID can only reveal existence (403 vs 404), not content.
- `/company/[slug]` — slug is derived from the company's own name (`slugify(name)`), not random; guessable if the company's name is known or guessed.

So there is no open IDOR today — authorization already gates content access. The value of this change is closing the *enumeration/existence-probing* surface, and removing reliance on "the ID happens to be hard to guess" as any part of the security story going forward. **Decision (user, explicit):** proceed with the full primary-key migration to random UUIDs across the entire schema, not the lighter-weight "add a public_id column to just the exposed models" alternative that was offered and declined.

## 3. What does NOT change: the WordPress/Tutor LMS boundary

Every `wp_*` column (`wp_user_id`, `wp_course_id`, `wp_bundle_id`) is an ID **owned by WordPress**, not generated by our schema. These stay `Int` everywhere: `User.wp_user_id`, `Employee.wp_user_id`, `Package.wp_bundle_id`, `PackageCourse.wp_course_id`, `CourseDc3Metadata.wp_course_id`, `EmployeeCourse.wp_course_id`, `Certificate.wp_course_id`. The WordPress bridge client (`lib/wordpress-bridge.ts`), the SSO auto-login URL builder (`buildWordPressCourseLaunchUrl`), and the webhook/poll sync paths (`lib/employee-learning.ts`) are unaffected by this migration — confirm this boundary explicitly in the implementation plan so nobody accidentally sweeps a `wp_*` column into the UUID conversion.

## 4. ID format

**Standard UUID v4** via Postgres's native `gen_random_uuid()` (built into Postgres 13+, no extension needed — confirmed available on Supabase). Prisma:

```prisma
id String @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
```

Note: plain `@default(uuid())` was considered first but rejected — it's a **Prisma-Client-side** default (the client generates the UUID and sends it explicitly on every `INSERT`), not a database-level one. Confirmed via a real `prisma migrate diff` run against this schema: with `@default(uuid())` the generated SQL added every `id` column with no `DEFAULT` clause at all. That would silently break any insert path that doesn't go through Prisma Client — specifically the `load-testing/seeders/*.js` scripts, which insert via the raw `pg` driver. `@default(dbgenerated("gen_random_uuid()"))` pushes the default to Postgres itself, so it fires for every insert path uniformly. Confirmed working: the corrected diff includes `DEFAULT gen_random_uuid()` on all 16 `id` columns.

Every FK column referencing a migrated model's `id` becomes `String @db.Uuid` to match. Rejected UUID v7 (time-ordered, better B-tree index locality on very large/high-insert tables) — the extra complexity (no native Postgres function for v7 on the current version; would need an app-level library) isn't justified at this project's scale, and the security property (unguessable) is identical between v4 and v7 given both carry well over 100 bits of randomness in the non-timestamp portion.

Native `uuid` column type (not `text`/`varchar`) for compact storage (16 bytes vs. 36-character string) and DB-level format validation.

## 5. Certificate folio stays human-readable: a separate sequence

`Certificate.reference_number` (format `D360-YYYY-MMDD-{employeeId}-{wp_course_id}`, built by `buildCertificateFolio` in `lib/employee-learning.ts:38`) currently embeds the employee's numeric ID directly. Once `Employee.id` is a UUID, that format breaks (unreadable, oversized for an official document number).

**Decision (user, explicit):** add a new column, decoupled from any primary key:

```prisma
model Certificate {
  ...
  folio_sequence Int @default(autoincrement())
  ...
}
```

New folio format: `D360-YYYY-MMDD-{paddedFolioSequence}-{wp_course_id}` (e.g. `D360-2026-0818-000047-900101`). `wp_course_id` stays in the folio unchanged (it's WordPress's ID, not ours, and already numeric/stable per §3). `buildCertificateFolio`'s signature changes from `(employeeId, courseId, completedAt)` to `(folioSequence, courseId, completedAt)` — the call site (`lib/employee-learning.ts`, inside `upsertEmployeeCertificatesFromBridge`) needs to read back the auto-assigned `folio_sequence` after insert (Postgres assigns it at `INSERT` time; Prisma's `create()` returns it in the result) rather than compute it from `employeeId`.

## 6. Migration strategy: truncate + rebuild, not value-preserving

**User confirmed:** current data is 100% disposable test/seed data — no real companies yet. This removes the need for a value-preserving migration (mapping every existing `Int` row to a fresh UUID while rewriting every FK reference in lockstep across 16 tables), which is by far the highest-risk, highest-effort part of a PK-type migration on a live system. Instead:

1. Update `prisma/schema.prisma` fully (all 16 models' `id` + every FK column identified in §2, plus the new `folio_sequence` column).
2. Migration truncates the affected tables and recreates the changed columns with their new types — this repo cannot use `prisma migrate dev` for *any* migration due to a pre-existing, unrelated bug (a May-2026 migration fails shadow-database replay even though the real database has zero drift; already documented and worked around twice in this repo's history — G-2's `Job` table and G-5's `dc3_pdf_url` column both used the same fix). The established safe pattern applies again: diff the live DB against the target schema, apply via `prisma migrate deploy`, never `migrate dev`. Note: Prisma 7 removed the `--from-url` flag used in earlier fixes this session — the current syntax is `prisma migrate diff --from-config-datasource --to-schema=prisma/schema.prisma --script` (confirmed working; `--from-config-datasource` reads `DIRECT_URL` from `prisma.config.ts`, same connection the old `--from-url "$DIRECT_URL"` pointed at).
3. After the schema migration lands, re-seed with `prisma/seed.ts` (demo users) if desired; `load-testing/seeders/` needs review (§7) before it can seed again too.

No maintenance-window coordination needed beyond "the app will 500 on any request touching a migrated table for the few seconds the migration runs" — acceptable per user, no real traffic today.

## 7. Code-impact map

Every location that currently treats one of these IDs as `number` needs to become `string`, with UUID-format validation replacing `Number.isInteger` checks. This spans (non-exhaustive — the implementation plan enumerates exact files):

- **Route params**: `app/api/certificates/[id]/dc3/route.ts`, `app/api/certificates/zip/route.ts` (already ID-free, filters by session), `app/(portal)/superadmin/companies/[id]/*`, `app/(portal)/superadmin/packages/[id]/*` — every `Number(id)` + `Number.isInteger(id)` pair becomes a UUID-string passthrough + regex/format check.
- **Server actions**: every `Number(formData.get("empresa_id"))`-shaped call across `app/(portal)/**/actions.ts` (packages, employees, dc3, reports, companies — the same call sites already touched across the G-1 through G-5 work in this conversation).
- **`lib/tenant-context.ts`**: `getActiveCompanyId(): number | null` → `string | null`; `enterCompanyContext(companyId: number)` → `(companyId: string)`. The scoping logic inside `lib/prisma.ts`'s tenant-guard `$extends` block is type-agnostic (just injects `company_id` into `where`/`data`) and needs no logic change, only the type flowing through it.
- **Session/JWT (`auth.ts`, `auth.config.ts`)**: **no change** — `user.id` is already carried as `String(usuario.id)` end-to-end (confirmed by reading the current `auth.ts`), so NextAuth's session/JWT layer is already UUID-ready.
- **Blob paths** (`lib/dc3-pdf.ts`, `app/api/upload/company-logo/route.ts`, `app/api/upload/instructor-signature/route.ts`, from the just-shipped PR #12): path construction is already string template literals (`` `constancias/${companyId}/${employeeId}/dc3-${certificateId}.pdf` ``) — works unchanged with UUID strings, just produces longer paths. No code change needed here beyond the type annotations flowing in.
- **`lib/course-sync.ts` / `lib/jobs.ts`** (G-2's async job engine): `PackageEnrollmentSyncPayload`'s `companyId: number`, `employeeIds: number[]`, `processedEmployeeIds: number[]` become `string`/`string[]` — this is JSON stored in `Job.payload`, so there's no DB-level type enforcement, but every read/write site in `lib/jobs.ts` needs updating together (`processPackageEnrollmentSyncJob`, `enqueuePackageEnrollmentSyncJob` in `lib/course-sync.ts`).
- **`lib/employee-learning.ts`**: `buildCertificateFolio` per §5; every `employeeId: number` parameter across the sync pipeline (`upsertEmployeeCertificatesFromBridge`, `syncEmployeeLearningFromBridgeSnapshot`, `scheduleEmployeeLearningSync`, etc.).
- **`lib/auditing.ts`**: `createAuditEvent`/`createSeatHistoryEntry` helpers take `entityId`/`companyId`/`actorUserId` — signatures change from `number` to `string`.
- **`prisma/seed.ts`**: creates demo users/companies with hardcoded assumptions about ID shape (needs audit — likely fine since it never hardcodes a specific ID, but confirm).
- **`load-testing/seeders/*.js`**: bulk-insert helpers (`seeders/lib/db.js`'s `bulkInsert`) and the seed scripts (01–04) currently capture `RETURNING id` values as JS numbers and do arithmetic/range assumptions in a few places (e.g., `wp_user_id` sequential assignment — that one's fine, WordPress ID stays Int; but any place assuming `employee.id`/`company.id` is a small int for constructing test fixtures needs a look). This is CommonJS, untyped — TypeScript won't catch mistakes here, needs manual review + a smoke-test seed run.

## 8. Verification approach

No test suite exists in this repo (confirmed in `CLAUDE.md`). Primary safety net: **TypeScript itself** — changing 16 Prisma models' ID types regenerates the Prisma Client with `string` fields everywhere those IDs flow, so `npx tsc --noEmit` will surface almost every call site that still assumes `number` as a compile error. This migration is unusually well-suited to "let the compiler find it" precisely because the type change is so pervasive and mechanical.

After `tsc`/`lint`/`build` are clean:
1. Re-seed (`prisma/seed.ts`, then `load-testing/` seeders once updated) against the migrated schema.
2. Manual smoke test: login as all 3 roles, view a company, view/download a certificate (confirms Blob path + folio still work), upload a company logo and an instructor signature (confirms the two upload routes), trigger a package sync (confirms the G-2 job engine's `Job.payload` string IDs round-trip correctly through a real chunked run), edit DC-3 metadata (confirms cache invalidation still matches on the new ID types).

## 9. Out of scope for this design

- Zero-downtime migration tooling (expand-contract) — not needed per §6.
- Adding a *separate* opaque public-facing token distinct from the PK (the lighter alternative that was proposed and declined) — superseded by the full PK migration.
- Any change to `wp_*` columns or WordPress-side identifiers (§3).
- Re-auditing authorization checks on the four exposed routes — they were already found adequate (§1); this migration is defense-in-depth on top of them, not a replacement for them.

## 10. Implementation plan note

Given the size (16 models, 40+ application files, a data-destructive migration, and a Prisma-client-wide type change), the implementation plan should likely be split into a small number of ordered sub-plans rather than one flat task list — e.g., (1) schema + migration + Prisma client, (2) core cross-cutting libs (`tenant-context`, `auditing`, `course-sync`/`jobs`, `employee-learning`/folio), (3) routes + server actions by feature area, (4) seeders + manual smoke test. `writing-plans` should make this call once it has the full file inventory in front of it.
